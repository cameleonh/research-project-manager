# Finishing Workflow

이 문서는 연구질문 생성과 분석은 빠르지만 원고 마무리가 병목인 연구자를 위한 논문 종료 흐름이다. 목표는 더 많은 아이디어를 만드는 것이 아니라, 이미 70-90% 진행된 연구를 투고 가능한 원고로 닫는 것이다.

## 핵심 판단

연구자의 병목이 어디에 있는지 먼저 구분한다.

- 앞단 병목: 리서치갭, 연구질문, 자료, 분석설계가 느림
- 뒷단 병목: 결과 압축, 주장 잠금, 한계 처리, 투고 판정이 느림

이 workflow는 뒷단 병목에 쓴다. 연구질문을 새로 만들거나 분석을 더 넓히는 workflow가 아니다.

## 한 줄 원칙

80% 연구 3편을 100% 투고본으로 바꾸는 것이 새 연구 3편을 더 여는 것보다 우선이다.

## 기본 흐름

```text
1. 연구질문을 한 문장으로 잠근다.
2. 분석한다.
3. VARIABLE_AUDIT로 실제 데이터 컬럼-코드 변수명-원고 변수를 검증한다.
4. ANALYSIS_DASHBOARD로 분석-결과-원고 위치를 잠근다.
5. Result.md에 결과를 표/그림 중심으로 넣는다.
6. Discussion.md에서 해석 강도를 조절한다.
7. 새 아이디어는 PARKING_LOT로 뺀다.
8. CITATION_AUDIT로 본문 인용-참고문헌 목록-실재 확인을 검증한다.
9. FINAL_AUDIT로 코드/변수-원고 내용-인용/참고문헌을 통합 점검한다.
10. SUBMISSION_CHECKLIST로 투고 가능 여부를 판정한다.
11. 투고한다.
```

## 단계별 기준

### 1. 연구질문 잠금

논문 하나에는 핵심 연구질문 하나를 둔다. 연구질문이 두 개 이상이면 둘 중 하나를 후속연구로 빼거나, 하나를 보조질문으로 낮춘다.

점검 질문:

- 이 논문이 답하려는 질문은 한 문장으로 무엇인가?
- 이 논문이 답하지 않을 질문은 무엇인가?
- 제목, 초록, 결론이 같은 질문을 향하고 있는가?

결과물:

- `START_HERE.md`의 `지금 붙잡은 질문`
- `06_manuscript/00_paper_outline.md`의 핵심 주장
- 필요하면 `DECISIONS.md`의 연구질문 잠금 기록

### 2. 분석

분석은 연구질문에 필요한 만큼만 한다. 새 분석을 시작하기 전에 이 분석이 투고 가능성을 높이는지, 아니면 투고를 늦추는지 판단한다.

점검 질문:

- 이 분석이 핵심 주장 방어에 필수인가?
- 같은 주장을 기존 표/그림으로 이미 보여줄 수 있는가?
- 이 분석이 없으면 심사에서 치명적인가?

결과물:

- `04_analysis/`의 스크립트
- `07_outputs/`의 결과 폴더
- `VARIABLE_AUDIT.md`
- 분석이 많으면 `ANALYSIS_DASHBOARD.md`

### 3. 분석-결과-원고 위치 잠금

분석이 여러 개면 `ANALYSIS_DASHBOARD.md`를 만든다. 분석 ID마다 목적, 스크립트, 결과 폴더, 원고 위치, 지원하는 주장을 연결한다.

결과를 원고에 쓰기 전에는 `VARIABLE_AUDIT.md`로 실제 데이터 컬럼, 코드 변수명, 원고/개념상 변수명, 측정 내용, 변환/코딩이 맞는지 확인한다. 변수 검증 상태가 `확인 전`, `불일치`, `애매함`, `수정 필요`이면 결과 해석을 확정하지 않는다.

점검 질문:

- 이 결과가 어느 스크립트에서 나왔는가?
- 이 결과가 어느 결과 폴더에 저장되어 있는가?
- 이 결과가 원고 어느 절에 들어가는가?
- 이 결과가 어떤 주장을 지원하는가?

상태 기준:

- `완료`: 코드가 실행됐고 결과가 저장됨
- `검증필요`: 숫자, 표본, 산식, 해석을 다시 봐야 함
- `원고반영`: 원고 본문, 표, 그림에 반영됨

### 4. 결과장 작성

`Result.md`는 분석 결과를 보여주는 장이다. 큰 해석과 정책적 함의는 `Discussion.md`로 보낸다.

점검 질문:

- 결과장이 표/그림 순서대로 읽히는가?
- 각 표/그림이 연구질문에 직접 답하는가?
- 불필요한 robustness나 부가분석이 본문을 흐리지 않는가?

결과물:

- `06_manuscript/Result.md`
- 표/그림 파일
- 본문과 표/그림 번호의 일치

### 5. 논의장 작성

`Discussion.md`에서는 결과의 의미를 설명하되, 주장 강도를 낮출 부분은 낮춘다. 이미 알고 있는 약점은 숨기는 것이 아니라 한계 또는 후속연구로 배치한다.

점검 질문:

- 이 결과로 말할 수 있는 것은 무엇인가?
- 이 결과로 말하면 안 되는 것은 무엇인가?
- 예상 비판 중 무엇은 수정했고, 무엇은 한계로 남겼는가?

결과물:

- `06_manuscript/Discussion.md`
- 한계 문단
- 후속연구 문단

### 6. 새 아이디어 분리

새 아이디어가 생기면 먼저 현재 논문에 필수인지 판단한다. 필수가 아니면 `PARKING_LOT.md`에 둔다.

판단 기준:

- 필수: 없으면 핵심 주장이 방어되지 않음
- 선택: 있으면 좋지만 없어도 투고 가능
- 후속: 별도 논문으로 더 적합함
- 삭제: 흥미는 있지만 자료·시간·논문 범위와 맞지 않음

결과물:

- `PARKING_LOT.md`의 보류 아이디어
- `이번 논문에서 주장하지 않을 것`

### 7. 인용과 참고문헌 검증

투고 직전에는 `CITATION_AUDIT.md`로 본문 인용, 참고문헌 목록, 인용 논문의 실재성을 확인한다. 검색 결과 제목만으로는 충분하지 않다. DOI resolver, publisher page, Crossref, PubMed, KCI, RISS, DBpia, Scopus 등 확인 가능한 출처와 확인일을 남긴다.

점검 질문:

- 본문에 인용한 모든 항목이 참고문헌 목록에 있는가?
- 참고문헌 목록의 모든 항목이 본문에서 인용되었거나 제외 사유가 있는가?
- 저자, 연도, 제목, 학술지, 권호, 페이지, DOI가 맞는가?
- 핵심 인용 논문은 DOI 또는 공식 학술 DB에서 실제 존재를 확인했는가?

결과물:

- `CITATION_AUDIT.md`
- 수정된 참고문헌 목록
- 미확인 인용의 다음 행동

### 8. 최종 audit

`FINAL_AUDIT.md`는 코드부터 인용 문헌까지 닫는 마지막 gate다. `audit variables`, `audit content`, `audit citations`, `audit final --strict` 순서로 확인한다.

점검 질문:

- 코드에서 사용한 변수가 실제 데이터 컬럼과 원고 변수 설명에 연결되는가?
- 원고 장별 파일에 placeholder나 빠진 장이 없는가?
- 본문 인용과 참고문헌 목록이 양방향으로 맞는가?
- 인용 논문 실재 확인 근거가 남아 있는가?
- 최종 audit blocker가 `제외` 사유 없이 남아 있지 않은가?

결과물:

- `FINAL_AUDIT.md`
- `START_HERE.md`의 남은 첫 수정 행동
- `WBS.md`의 최종 blocker 상태

### 9. 투고 가능 판정

원고가 어느 정도 닫히면 `SUBMISSION_CHECKLIST.md`를 연다. 이 파일은 할 일 목록이 아니라 투고 가능 판정표다.

점검 질문:

- 새 분석 없이 투고 가능한가?
- 남은 수정이 문장, 형식, 표기 수준인가?
- 표본 수, 변수 정의, 핵심 계수, 본문 수치가 일치하는가?
- `VARIABLE_AUDIT.md`의 핵심 변수 검증 상태가 모두 해결되었는가?
- `CITATION_AUDIT.md`의 본문-목록 대조와 실재 확인 상태가 모두 해결되었는가?
- `FINAL_AUDIT.md`와 `audit final --strict`가 통과했는가?
- 제목, 초록, 결론이 같은 주장을 하는가?

결과물:

- `SUBMISSION_CHECKLIST.md` 최종 판정
- 남은 필수 수정 3개
- 투고일

### 10. 투고

투고는 연구의 끝이 아니라 심사대 위에 올리는 단계다. 완벽한 원고를 기다리기보다, 심사받을 수 있는 원고를 제출한다.

점검 질문:

- 타깃 학술지 양식을 맞췄는가?
- 커버레터, 초록, 키워드, 참고문헌, 표/그림 파일이 준비됐는가?
- 투고본과 내부 작업본을 구분해 저장했는가?

결과물:

- `07_outputs/submission_YYYY-MM-DD/`
- 제출 원고
- 제출 표/그림
- 커버레터
- 투고 확인 기록

## 예상 비판 처리표

이미 생각한 비판은 원고 안에서 처리해야 한다. 머릿속에만 있으면 외부에서는 아직 약점으로 보인다.

| 예상 지적 | 내 판단 | 원고 처리 |
|---|---|---|
| 데이터 대표성 약함 | 일반화 제한 인정 | 한계 문단 |
| 인과 주장 어려움 | 관련성/패턴 분석으로 낮춤 | 제목·초록 표현 조정 |
| 추가 변수 필요 | 있으면 좋지만 현재 논문 필수 아님 | PARKING_LOT |
| 해석 과장 위험 | 강도 조절 필요 | 논의 문장 수정 |

## 피해야 할 패턴

- 새 연구를 열어 마무리 불안을 피한다.
- 심사자가 볼 약점을 숨긴다.
- 한 논문에 연구질문을 두세 개 넣는다.
- robustness를 계속 추가해 본문 주장을 흐린다.
- `PARKING_LOT.md`에 넣은 아이디어를 다시 본문으로 끌어온다.
- `SUBMISSION_CHECKLIST.md`를 끝없는 작업 목록으로 바꾼다.

## 좋은 마무리 질문

피드백을 받을 때는 아이디어를 더 달라고 묻지 않는다. 이렇게 묻는다.

```text
이 원고가 투고 가능한지 봐주세요.
반드시 고칠 것 3개와 한계로 남겨도 되는 것 3개를 나눠주세요.
추가 분석 제안은 필수 보완인지 후속연구인지 구분해주세요.
```

## 관련 파일

- `START_HERE.md`: 지금 붙잡은 질문과 다음 첫 행동
- `ANALYSIS_DASHBOARD.md`: 분석-결과-원고 위치 연결
- `VARIABLE_AUDIT.md`: 실제 데이터 컬럼-코드 변수명-원고 변수명 대조
- `CITATION_AUDIT.md`: 본문 인용-참고문헌 목록-실재 확인 대조
- `FINAL_AUDIT.md`: 코드/변수-원고 내용-인용/참고문헌 최종 통합 판정
- `06_manuscript/Result.md`: 결과장
- `06_manuscript/Discussion.md`: 논의장
- `PARKING_LOT.md`: 이번 논문에서 뺄 아이디어
- `SUBMISSION_CHECKLIST.md`: 투고 가능 판정
